1. Objetivo de la sesión

Al finalizar esta sesión, el aprendiz será capaz de explicar la diferencia entre autenticación (quién eres) y autorización/permisos (qué puedes hacer), configurar autenticación por JWT con SimpleJWT, y proteger endpoints usando clases de permisos estándar y personalizadas.

2. Autenticación vs. permisos

Hasta ahora nuestra API es completamente abierta: cualquiera puede crear, editar o borrar libros. En un proyecto real eso es inaceptable. DRF separa el problema en dos capas independientes:

CapaPregunta que respondeEjemplo
Autenticación¿Quién está haciendo la petición?Un token JWT válido identifica al usuario "carlos".
Permisos¿Puede ese usuario hacer esta acción?"carlos" está autenticado, pero solo un administrador puede borrar libros.
💡 Idea clave
Un usuario puede estar perfectamente autenticado (DRF sabe quién es) y aun así no tener permiso para una acción específica. Son dos preguntas distintas y DRF las resuelve con dos configuraciones distintas: authentication_classes y permission_classes.
3. Autenticación con JWT (SimpleJWT)

Paso 1: Instalación

pip install djangorestframework-simplejwt

Paso 2: Configuración global en settings.py:

REST_FRAMEWORK = {
    'DEFAULT_AUTHENTICATION_CLASSES': [
        'rest_framework_simplejwt.authentication.JWTAuthentication',
    ],
    'DEFAULT_PERMISSION_CLASSES': [
        'rest_framework.permissions.IsAuthenticated',
    ],
}

Paso 3: Rutas para obtener y refrescar el token en config/urls.py:

from rest_framework_simplejwt.views import TokenObtainPairView, TokenRefreshView

urlpatterns = [
    # ...
    path('api/token/', TokenObtainPairView.as_view(), name='token_obtain_pair'),
    path('api/token/refresh/', TokenRefreshView.as_view(), name='token_refresh'),
]

Paso 4: Obtener un token enviando usuario y contraseña de un superusuario ya creado (sesión 3):

POST /api/token/
{
    "username": "admin",
    "password": "tu_contraseña"
}

# Respuesta:
{
    "refresh": "eyJhbGciOi...",
    "access": "eyJhbGciOi..."
}

El access token se envía en cada petición protegida dentro del encabezado Authorization:

GET /biblioteca/libros/
Authorization: Bearer eyJhbGciOi...
4. Permisos: estándar y personalizados

DRF incluye clases de permisos listas para usar:

ClaseComportamiento
AllowAnyCualquiera puede acceder, autenticado o no.
IsAuthenticatedSolo usuarios autenticados (con token válido).
IsAdminUserSolo usuarios con is_staff=True.
IsAuthenticatedOrReadOnlyCualquiera puede leer (GET); solo autenticados pueden escribir (POST/PUT/DELETE).

Se pueden combinar por vista, sobreescribiendo la configuración global:

from rest_framework.permissions import IsAuthenticatedOrReadOnly
from rest_framework import viewsets
from .models import Libro
from .serializers import LibroSerializer

class LibroViewSet(viewsets.ModelViewSet):
    queryset = Libro.objects.all().order_by('titulo')
    serializer_class = LibroSerializer
    permission_classes = [IsAuthenticatedOrReadOnly]

Cuando la regla de negocio no encaja en las clases estándar, se crea un permiso personalizado heredando de BasePermission:

from rest_framework.permissions import BasePermission

class EsBibliotecarioOSoloLectura(BasePermission):
    """Solo el grupo 'bibliotecarios' puede escribir; el resto solo puede leer."""

    def has_permission(self, request, view):
        if request.method in ('GET', 'HEAD', 'OPTIONS'):
            return True
        return request.user.is_authenticated and request.user.groups.filter(name='bibliotecarios').exists()
5. Ejercicio práctico (para hacer en clase)
  1. Instala djangorestframework-simplejwt y configura las rutas /api/token/ y /api/token/refresh/.
  2. Obtén un token con las credenciales de tu superusuario y verifica que puedas usar el access token para acceder a un endpoint protegido.
  3. Configura DEFAULT_PERMISSION_CLASSES globalmente como IsAuthenticated y confirma que, sin token, la API responde 401.
  4. Cambia el permiso de al menos un ViewSet a IsAuthenticatedOrReadOnly y verifica que el listado (GET) siga siendo público mientras que crear/editar/borrar requieran autenticación.
  5. Crea un permiso personalizado que restrinja una acción de escritura a un grupo específico de usuarios.
  6. Documenta en tu README cómo obtener un token y qué endpoints requieren autenticación.
6. Errores comunes
✗Enviar el token sin el prefijo Bearer en el encabezado Authorization → DRF no reconoce el token y responde 401.
✗Confundir el token access (de corta duración, para autenticar peticiones) con el refresh (para obtener un nuevo access token) y usar el equivocado.
✗Definir un permiso personalizado y olvidar implementar has_permission (o has_object_permission para permisos a nivel de objeto) → DRF usa el comportamiento por defecto, normalmente permitir todo.
✗Configurar IsAuthenticated de forma global y olvidar que eso también bloquea la Browsable API para usuarios anónimos durante las pruebas.
