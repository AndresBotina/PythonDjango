1. Objetivo de la sesión

Al finalizar esta sesión, el aprendiz será capaz de identificar cuándo un ModelViewSet se queda corto, escribir una vista con APIView para tener control total sobre la lógica, y usar Generic Views como un punto intermedio entre el control manual de APIView y la automatización total de ModelViewSet.

2. ¿Por qué no siempre alcanza con ModelViewSet?

ModelViewSet es excelente para CRUDs estándar, pero en el mundo real casi siempre aparece lógica de negocio que no encaja en el molde genérico: por ejemplo, que crear un libro también descuente stock de otro recurso, que una acción dependa del usuario autenticado, o que un endpoint no represente un modelo completo sino una operación puntual (como "marcar como prestado").

DRF ofrece tres niveles de abstracción, de más manual a más automático:

NivelClase baseCuándo usarla
ManualAPIViewNecesitas control total: lógica de negocio particular, combinar varios modelos, respuestas no estándar.
IntermedioGeneric Views (ListCreateAPIView, etc.)Es casi un CRUD estándar, pero quieres personalizar un detalle puntual (por ejemplo, el queryset o quién puede ver qué).
AutomáticoModelViewSetCRUD estándar sin reglas especiales (lo que usamos en la sesión 7).
💡 Idea clave
No se trata de "cuál es mejor": se trata de elegir la herramienta según cuánto control necesitas. Empezar siempre por ModelViewSet y bajar de nivel solo cuando el genérico no alcance es la práctica recomendada.
3. APIView: control total

APIView es la clase base de la que heredan todas las demás. Cada verbo HTTP se implementa como un método de la clase (get, post, put, delete):

from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework import status
from .models import Libro
from .serializers import LibroSerializer

class LibroDisponibleAPIView(APIView):
    """Devuelve solo los libros marcados como disponibles."""

    def get(self, request):
        libros = Libro.objects.filter(disponible=True)
        serializer = LibroSerializer(libros, many=True)
        return Response(serializer.data)

    def post(self, request):
        serializer = LibroSerializer(data=request.data)
        serializer.is_valid(raise_exception=True)
        serializer.save()
        return Response(serializer.data, status=status.HTTP_201_CREATED)

Con APIView decidimos manualmente qué queryset usar, qué serializer aplicar y qué código de estado devolver en cada caso. Es exactamente el mismo control que ya practicamos en la sesión 5 con @api_view, pero organizado como clase.

Conéctala en urls.py como una vista de clase, usando .as_view():

from django.urls import path
from . import views

urlpatterns = [
    path('libros/disponibles/', views.LibroDisponibleAPIView.as_view(), name='libros_disponibles'),
]
4. Generic Views: el punto intermedio

Las Generic Views ya traen implementada la lógica común (listar, crear, actualizar, borrar) pero permiten personalizar puntos clave sobreescribiendo atributos o métodos:

from rest_framework import generics
from .models import Libro
from .serializers import LibroSerializer

class LibroListCreateView(generics.ListCreateAPIView):
    serializer_class = LibroSerializer

    def get_queryset(self):
        # Personalización: solo libros disponibles, ordenados por título
        return Libro.objects.filter(disponible=True).order_by('titulo')

class LibroDetailView(generics.RetrieveUpdateDestroyAPIView):
    queryset = Libro.objects.all()
    serializer_class = LibroSerializer

Aquí el listado (GET) y la creación (POST) quedan resueltos por ListCreateAPIView, pero personalizamos get_queryset() para filtrar solo los disponibles. La clase RetrieveUpdateDestroyAPIView resuelve detalle, actualización y borrado sin código adicional.

5. Ejercicio práctico (para hacer en clase)
  1. Identifica una regla de negocio de tu proyecto que un ModelViewSet genérico no resolvería directamente (ej. "solo mostrar los productos con stock" o "solo permitir crear si el usuario cumple una condición").
  2. Implementa esa regla en una clase APIView, sobreescribiendo el método get o post según corresponda.
  3. Conecta tu APIView a una ruta específica (distinta de las generadas por el router) en urls.py usando .as_view().
  4. Reescribe el mismo endpoint usando una Generic View apropiada (ListCreateAPIView, RetrieveUpdateDestroyAPIView, etc.) sobreescribiendo get_queryset().
  5. Compara ambas implementaciones y anota en un comentario cuántas líneas de código ahorró la Generic View frente al APIView manual.
  6. Verifica en la Browsable API que ambas versiones del endpoint (APIView y Generic View) devuelven el mismo resultado.
6. Errores comunes
✗Olvidar .as_view() al conectar un APIView o Generic View en urls.py → error TypeError: view must be a callable.
✗Implementar un método HTTP que no corresponde a la Generic View elegida (por ejemplo, esperar que ListCreateAPIView soporte DELETE) → error 405 Method Not Allowed.
✗Olvidar raise_exception=True en is_valid() dentro de un APIView manual y no manejar el caso de error a mano → la vista falla silenciosamente o con una excepción no controlada.
✗Definir queryset y get_queryset() al mismo tiempo sin necesidad → confusión sobre cuál tiene prioridad (siempre gana get_queryset() si está definido).
