1. Objetivo de la sesión

Al finalizar esta sesión, el aprendiz tendrá un CRUD completo, coherente y probado de punta a punta para todos los recursos principales de su proyecto, integrando serializers (sesión 6), ViewSets/Routers (sesión 7) y, donde haga falta, APIView/Generic Views (sesión 9).

2. ¿Qué significa un CRUD "completo y consistente"?

No basta con que cada operación individual funcione: un CRUD completo también debe ser consistente en sus respuestas. Eso significa:

AspectoQué revisar
Códigos de estado201 al crear, 200 al listar/actualizar, 204 al borrar, 400 ante datos inválidos, 404 si el recurso no existe.
Formato de erroresLos errores de validación deben llegar como JSON legible (serializer.errors), no como una página de error HTML de Django.
RelacionesLos campos de relación (ForeignKey) deben mostrar información útil (ej. el nombre, no solo el ID) sin romper la creación/actualización.
Orden y filtros básicosLos listados deben tener un orden predecible (order_by) aunque sea simple, antes de agregar filtros avanzados en la sesión 13.
💡 Idea clave
Un endpoint que "funciona" en el caso feliz pero devuelve un error 500 crudo ante datos inválidos no está terminado. Probar el camino del error es tan importante como probar el camino exitoso.
3. Ejemplo guiado: revisión end-to-end del CRUD de Biblioteca

Retomando el proyecto "Biblioteca", vamos a probarlo de punta a punta usando la documentación interactiva (Browsable API) en /biblioteca/libros/:

# 1) Listar (GET) — debe responder 200 con un array JSON
GET /biblioteca/libros/

# 2) Crear (POST) con datos válidos — debe responder 201
POST /biblioteca/libros/
{
    "titulo": "El túnel",
    "autor": 1,
    "precio": 38000,
    "disponible": true
}

# 3) Crear (POST) con datos inválidos — debe responder 400, no 500
POST /biblioteca/libros/
{
    "titulo": "",
    "autor": 1,
    "precio": -100
}

# 4) Ver detalle (GET) — debe responder 200 o 404 si no existe
GET /biblioteca/libros/99/

# 5) Actualizar parcial (PATCH) — debe responder 200
PATCH /biblioteca/libros/1/
{ "disponible": false }

# 6) Borrar (DELETE) — debe responder 204 sin contenido
DELETE /biblioteca/libros/1/

Si el paso 3 devuelve un error 500 en lugar de 400, revisa que el serializer tenga las validaciones de la sesión 6 y que la vista use ModelViewSet o llame is_valid(raise_exception=True) correctamente.

Consistencia en las relaciones: confirma que LibroSerializer siga exponiendo tanto autor (el ID, necesario para crear/actualizar) como autor_nombre (de solo lectura, útil para mostrar), como quedó definido en la sesión 6.

4. Ejercicio práctico (para hacer en clase)
  1. Ejecuta manualmente, sobre cada recurso principal de tu proyecto, la secuencia completa: listar, crear válido, crear inválido, detalle, actualización parcial y borrado.
  2. Anota el código de estado HTTP que devolvió cada paso y compáralo con la tabla de la sección 2.
  3. Si algún paso no devuelve el código esperado, corrige el serializer o la vista correspondiente.
  4. Agrega un order_by() razonable al queryset de cada listado si todavía no lo tiene.
  5. Verifica que los campos de relación (ForeignKey) muestren tanto el ID como un campo legible de solo lectura.
  6. Documenta en un archivo README.md de tu proyecto la lista de endpoints disponibles y qué método/código de estado espera cada uno.
5. Errores comunes
✗Un POST con datos inválidos devuelve error 500 en lugar de 400 → normalmente falta una validación en el serializer o se está usando una vista manual sin manejar is_valid() correctamente.
✗Un DELETE exitoso devuelve un cuerpo JSON en lugar de una respuesta vacía con 204 → suele pasar al sobreescribir destroy() sin llamar al comportamiento original.
✗Los listados no tienen orden definido → los resultados cambian de posición entre una petición y otra, dificultando las pruebas.
✗Exponer solo el ID de una relación sin ningún campo legible → el cliente de la API tiene que hacer peticiones adicionales para mostrar información básica.
